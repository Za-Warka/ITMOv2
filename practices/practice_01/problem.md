# Проблема и метрики

## Проблема

- Пользователь: внутренние сервисы и инженеры, вызывающие API `/api/reviews` для автоматизированного ревью PR по diff.
- Ситуация: добавлен сервис ревью и HTTP-эндпоинт, пересылающий diff во внешний LLM и возвращающий ответ клиенту.
- Что происходит сейчас: сырой diff передается в LLM без редактирования секретов; нет лимита размера и ответа 413; нет таймаута и обработчика ошибок; формат ответа не соответствует ожидаемому контракту; отсутствует валидация входа и Pydantic-модели; нет телеметрии (request_id, длительность, статус).
- Почему это мешает пользователю или бизнесу: риск утечки токенов/паролей/ключей в внешний LLM (безопасность и комплаенс), нестабильность интеграции (нет таймаутов и контролируемых ошибок), невозможность надежной интеграции из-за отсутствия гарантированного схемы ответа, потенциальная деградация API при больших payload без предсказуемого 413.
- Что не входит в задачу: реализация кода, изменения в GitHub (approve/merge/edit), запуск деплоя. Эта работа — формирование требований и проверок.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля ответов, соответствующих OUT-1 (есть `summary`, `risks` ≤3 с `file`,`line`,`evidence`,`risk`, и `checks`) | 0% (ручная проверка ответов сервиса на тестовом стенде) | 100% | на каждом релизе и nightly | интеграционные тесты сервиса ревью |
| Укрытие секретов по SEC-1 (удалены токены/пароли/приватные ключи до LLM) | 0% (юнит-тесты с фикстурами секретов) | 100% | на PR и nightly | юнит-тесты редактирования, статические проверки |

## Почему изменение метрики подтвердит решение проблемы

Если все ответы соответствуют контракту OUT-1, клиентские интеграции получают предсказуемую структуру без доработок и падений на парсинге. Если укрытие секретов достигает 100%, исключаем класс инцидентов с утечкой чувствительных данных во внешний LLM и соблюдаем комплаенс. Вместе эти метрики закрывают ключевые риски качества и безопасности для первого инкремента.

## Как использовали AI

- Для чего: выявление нарушений требований SEC-1, API-1, REL-1, OUT-1, OBS-1 в diff и формирование проверяемых рисков и чеков.
- Тип промпта: master prompt для повторного ревью (P1-02).
- Строка в [`prompts.md`](prompts.md): P1-02.
- Что проверили и исправили сами: соотнесли каждый риск со строками diff и правилами; ограничили список ровно тремя рисками; сформулировали проверки, воспроизводимые тестами; исключили любые действия вида approve/merge/edit.
