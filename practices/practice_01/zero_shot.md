Проблемы (по убыванию критичности)
- app/review_service.py:19-22 — Нарушение SEC-1: дифф отправляется во внешний LLM без редактирования секретов. Evidence: prompt собирается как f"Review this pull request and find problems:\n{diff}" и целиком передаёт diff наружу. Риск утечки токенов/паролей/ключей.
- app/review_service.py:19-22 — Нарушение OUT-1: контракт ответа не соблюдён. Сейчас возвращается {"comment": answer}, а по правилу OUT-1 нужно вернуть структуру с полями summary, risks (≤3, с file/line/evidence/risk), checks. Это приведёт к несовместимости клиентов и невозможности автоматизированной проверки.
- app/api.py:35-38 — Нарушение API-1: нет проверки длины diff и возврата 413 (Payload Too Large) при >20 000 символов. Сейчас любой размер попадёт в сервис и уйдёт в LLM.
- app/review_service.py:20-22 — Нарушение REL-1: нет таймаута 10 секунд для внешнего вызова и контролируемой обработки ошибок. Любая задержка/исключение LLM приведёт к подвешенному запросу или 500 без структурированного ответа.
- app/api.py:35-38 — Отсутствие валидации входа. Используется сырой dict, доступ по ключу payload"diff" без проверки. При отсутствии ключа будет KeyError → 422/500 вместо предсказуемой ошибки в заданном формате.
- app/api.py:35-38; app/review_service.py:19-22 — Нарушение OBS-1: отсутствует телеметрия (request_id, длительность, статус). При сбоях и SLA-контроле не будет метрик. Важно также не логировать содержимое diff и ответа модели.
- app/api.py:35-38 — Несоответствие схемы ответа/входа FastAPI-практикам. Нет Pydantic-моделей для запроса/ответа, что затруднит OpenAPI-спеки, валидацию и автогенерацию клиентов.
- app/review_service.py:9-13 — Ненужное изменение сигнатуры Protocol-метода с тела на многосрочную форму с ellipsis. Функционально не ломает, но шум в диффе без пользы и может смутить линтеры/типизацию. Минимизировать изменения лучше.
