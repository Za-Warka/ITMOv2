# Нагрузочные проверки

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| Валидный POST /api/reviews при стабильном LLM | 20 RPS, 5 минут | 5xx = 0; p50 < 200 мс; p95 < 500 мс | Латентность эндпоинта, распределение кодов ответов | OUT-1 (контракт ответа для e2e), OBS-1 (метрики без логирования содержимого); «Требуется решение команды: финальные пороги RPS/латентности и стенд» |
| POST /api/reviews с diff > 20000 | 5 RPS, 3 минуты | 100% запросов → HTTP 413; вызовы LLM = 0 | Долю 413, факт отсутствия внешних вызовов | API-1; app/api.py:35-37 — сейчас нет проверки размера и возврата 413 |
| Медленный LLM (>10с) под нагрузкой | 10 RPS, 5 минут; LLM-заглушка sleep 12с | 5xx = 0; 100% контролируемых ответов об ошибке; p95 времени ответа ≤ 11с | Долю контролируемых ошибок, устойчивость при таймауте | REL-1; app/review_service.py:21-22 — нет таймаута 10с сейчас; «Требуется решение команды: механизм заглушки/инструменты» |

Если нагрузочное тестирование пока не требуется, включать его после выполнения условий готовности: реализованы 413 для diff > 20000 (API-1), таймаут внешнего LLM 10с и контролируемая обработка ошибок (REL-1), базовая телеметрия без логирования содержимого запросов и ответов (OBS-1: только request_id, длительность, статус), а также доступен стенд с имитацией задержек LLM и генерацией крупных diff. До этого этапа нагрузка может маскировать функциональные дефекты и не даёт воспроизводимых результатов.

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): P1-03.
- Что проверили и исправили сами: синхронизировали сценарии с API-1/REL-1/OUT-1 и OBS-1; задали измеримые пределы и наблюдаемые метрики; неизвестные пороги и инструменты пометили «Требуется решение команды»; исключили логирование содержимого diff/ответа.
