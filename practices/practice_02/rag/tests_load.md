# Нагрузочные проверки (Практика 2)

## Введение и цели

Зачем: подтвердить, что сервис `/api/reviews` выдерживает целевую нагрузку и корректно соблюдает правила SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1 под разными профилями трафика.

Критерии успеха:
- Функциональные: соблюдение API-1 (вход > 20 000 символов → HTTP 413 без вызова внешнего LLM), REL-1 (таймаут внешнего LLM 10 с и контролируемый ответ), SEC-1/OBS-1 (отсутствие утечек секретов и отсутствует логирование содержимого diff/ответа), OUT-1 (структура ответа: summary, risks ≤3, checks), QA-1 (риски подтверждены).
- Производительные: целевые p50/p90/p99 латентности, устойчивый RPS, допустимая доля 4xx/5xx, отсутствие таймаутов приложения и приемлемая загрузка CPU/Memory. Конкретные пороги, не заданные правилами, помечены как «Требуется решение команды».

## Метрики и пороги (pass/fail)

Измеряем:
- Латентность p50/p90/p99 по `/api/reviews`.
- Пропускная способность (целевой и фактический RPS).
- Доли 2xx/4xx/5xx и отдельно частоты 413 (API-1).
- Таймауты приложения и клиента.
- Нагрузку CPU/Memory сервиса (если телеметрия доступна).
- Для REL-1: доля запросов, завершившихся контролируемым ответом при таймауте внешнего LLM 10 с.
- Для SEC-1/OBS-1: нулевой счётчик утечек по шаблонам в логах; отсутствие логирования содержимого diff/ответа модели.
- Для OUT-1/QA-1: валидность структуры ответа; `risks` <= 3; риски подтверждены.

Пороговые значения:
- API-1: вход > 20 000 символов → 100% HTTP 413; 0 вызовов внешнего LLM.
- REL-1: внешний LLM имеет таймаут 10 с; сервис возвращает контролируемый ответ. Допустимая серверная латентность ответа и SLA — Требуется решение команды.
- Остальные числовые пороги (p50/p90/p99, RPS-цели, CPU/Memory, допускаемые 4xx/5xx, N, X) — Требуется решение команды.

## Среда, инструменты и безопасность

Инструмент нагрузки: k6 (локально или в контейнере). Версию k6 фиксировать в Evidence.

Стенд:
- Доступный HTTP endpoint сервиса `/api/reviews` (стабильная сборка).
- Заглушка внешнего LLM: HTTP-сервис, умеющий задерживать ответ >10 с и считать обращения. Способ подключения к сервису — Требуется решение команды.
- Телеметрия (опционально): Prometheus/Grafana или аналог, метрики CPU/Memory и ошибки.

Безопасность (связь с SEC-1/OBS-1):
- В тестовых данных использовать синтетические шаблоны «секретов» (например, `secret_TEST_xxx`, `AKIA...TEST`).
- Запрещено логировать содержимое diff и ответов модели; в логи писать только `request_id`, длительность и статус.
- В Evidence сохранять только агрегаты и сэмплы логов без содержимого diff/ответов.

Данные:
- Генерируемые `diff` без реальных секретов.
- Длины `diff` настраиваемы для сценариев API-1 (<= 20 000 и > 20 000).

## Порядок запуска и воспроизводимость

Переменные окружения:
- `BASE_URL` — адрес сервиса (например, `http://localhost:8000`).
- `DIFF_SIZE` — длина тестового diff для обычных сценариев (например, 1000).
- `DIFF_SIZE_OVER` — длина diff для 413 (например, 20050).
- `LLM_DELAY_MS` — задержка заглушки LLM (например, 12000 для REL-1). Настройка маршрутизации — Требуется решение команды.

Пример k6-скрипта `reviews_load.js` (схема, без логирования содержимого):

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  scenarios: {
    baseline: {
      executor: 'constant-arrival-rate', rate: 50, timeUnit: '1s', duration: '5m', preAllocatedVUs: 50,
    },
  },
  thresholds: {
    http_req_failed: ['rate==0'], // 5xx = 0 для baseline; иные пороги — Требуется решение команды
  },
};

function makeDiff(len) {
  const base = 'diff --git a/x b/x\n';
  return (base + 'A'.repeat(len)).substring(0, len);
}

export default function () {
  const url = `${__ENV.BASE_URL}/api/reviews`;
  const diffLen = Number(__ENV.DIFF_SIZE || 1000);
  const payload = JSON.stringify({ diff: makeDiff(diffLen) });
  const res = http.post(url, payload, { headers: { 'Content-Type': 'application/json' } });
  // Валидация OUT-1 без логирования содержимого
  check(res, {
    'status 2xx/4xx ok': (r) => r.status >= 200 && r.status < 500,
    'OUT-1 shape': (r) => {
      try { const j = r.json(); return j && j.summary !== undefined && Array.isArray(j.risks) && j.risks.length <= 3 && Array.isArray(j.checks); } catch(e) { return false; }
    },
  });
  sleep(0.01);
}
```

Запуски:
- Baseline: `k6 run -e BASE_URL=$BASE_URL -e DIFF_SIZE=1000 reviews_load.js`
- Ramp/Spike/Stress/Soak: изменить `options.scenarios` по описанию сценариев; зафиксировать rate/duration/ступени — Требуется решение команды.
- API-1 (413): `k6 run -e BASE_URL=$BASE_URL -e DIFF_SIZE=$DIFF_SIZE_OVER reviews_load.js` и ожидать 413. Для гарантий 413: отдельный скрипт со 100% payload > 20000.
- REL-1 (таймаут): настроить заглушку LLM на задержку `LLM_DELAY_MS > 10000`; прогнать Baseline/Ramp. Подтвердить контролируемые ответы и отсутствие 5xx.
- SEC-1/OBS-1: прогнать Baseline с синтетическими «секретами» в diff; проверить логи по шаблонам; совпадений = 0.

Сохранение Evidence:
- k6: `--summary-export out/summary.json`; полные выводы k6 сохранять в файл.
- Телеметрия: выгрузка графиков CPU/Memory/ошибок в PDF/PNG.
- Логи сервиса: выборка полей `request_id`, длительность, статус; без содержимого diff/ответов.
- Версии: k6, сервис (commit/tag), конфиг стенда, точные команды и параметры.

## Когда нагрузочные тесты откладываются

Тесты можно отложить, если одновременно верно:
- Endpoint `/api/reviews` не стабилен (частые функциональные изменения) или отсутствует изолированный стенд.
- Не реализованы защитные требования SEC-1/API-1/REL-1/OUT-1 (см. CONTEXT).
- Нет доступной телеметрии для базовых метрик (хотя бы latency и ошибки) — либо ее сбор нарушает OBS-1.

Триггеры включения тестов:
- Стабильный endpoint `/api/reviews` доступен и проходит функциональные проверки.
- Внедрены SEC-1, API-1, REL-1, OUT-1; логи соответствуют OBS-1.
- Доступна минимальная телеметрия по латентности и ошибкам; готова LLM-заглушка для REL-1.

## Как использовали AI

- AI помог структурировать сценарии (baseline, ramp, spike, stress, soak, граничные по правилам) и связать их с SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1.
- Проверено вручную: отсутствие логирования содержимого в примерах; явные ссылки на правила; все неопределенные пороги помечены «Требуется решение команды».
