# Нагрузочные проверки

Кратко: цель — подтвердить, что сервис `/api/reviews` предсказуемо работает под типовой и повышенной нагрузкой, соблюдает правила SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1, и предоставить воспроизводимые доказательства (Evidence).

Что считаем успешным:
- Функционально: вход > 20 000 символов всегда получает 413 без вызова внешнего LLM (API-1); при задержке внешнего LLM > 10 c сервис завершает вызов по таймауту 10 c с контролируемой обработкой (REL-1); логи не содержат diff/ответов/секретов (OBS-1/SEC-1); ответы соответствуют OUT-1 (summary, risks ≤ 3, checks) и не содержат действий approve/merge/edit (SCOPE-1/OUT-1).
- Нагрузочно: при согласованных профилях нагрузки соблюдаются целевые пороги латентности и ошибок, отсутствуют 5xx (кроме сценариев деградации/негативных), не наблюдается неконтролируемого роста потребления ресурсов.

Требуется решение команды: значения целевых RPS и некоторые пороги зависят от целей сервиса и стенда. Ниже указаны рекомендуемые значения по умолчанию, которые должны быть либо подтверждены, либо изменены.

## Сценарии и Evidence

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence | Инструмент/Стенд |
|---|---|---|---|---|---|
| Baseline: стабильная нагрузка POST /api/reviews с небольшими diff | 50 RPS, 10 мин, тело ~1-2 КБ синтетического diff | 5xx = 0; 4xx ≤ 1% (только валидация); p50 < 200 мс; p90 < 400 мс; p99 < 800 мс; CPU и Memory < 70% (если телеметрия есть) | Латентность p50/p90/p99, RPS, 5xx/4xx, timeouts, CPU/Memory | Отчёт k6 (JSON/summary), графики телеметрии, выдержки логов без содержимого diff/ответов | k6 OSS v0.49+; staging со стабильными лимитами и телеметрией |
| Ramp: плавный рост/снижение | 0→100 RPS за 10 мин, затем 100→0 RPS за 10 мин | 5xx = 0; p99 < 1000 мс; отсутствие резких ошибок при изменении нагрузки | Те же метрики + стабильность при изменении нагрузки | k6 summary с этапами, графики нагрузки/латентности | k6; staging |

| Stress: до начала деградации | Лестница 50→300 RPS, шаг 50, по 3 мин на шаг | Зафиксировать RPS начала деградации: критерий — p99 > 1500 мс или 5xx > 0 или timeouts > 0. Безопасный лимит = шаг до деградации | Порог деградации, поведение ошибок | Сводная таблица RPS→показатели, графики; протокол решения безопасного лимита | k6; staging |
| Soak: длительная выдержка | 30 RPS, 2 часа (включая 10 мин прогрева) | 5xx = 0; timeouts = 0; рост памяти процесса < 5% от уровня после прогрева; p90 < 500 мс | Ошибки, латентность, тренды CPU/Memory, GC/FD (если есть) | k6 summary, длительные графики телеметрии, проверка стабильности ресурсов | k6; staging со стабильной телеметрией |
| API-1: вход > 20 000 символов | 10 RPS, 5 мин, тело ~25 000 символов | 100% ответов = HTTP 413; 5xx = 0; вызов LLM не производится | Доля 413, отсутствие обращений к LLM | k6 summary по статусам; метрика/логи без вызовов LLM (счётчик) | k6; staging; метрика "llm_requests" или mock внешнего LLM |
| REL-1: таймаут внешнего LLM 10 с | 10 RPS, 10 мин; внешний LLM задерживает ответы > 10 с | Каждый запрос завершается за ≤ 11 с контролируемым ответом; 5xx = 0 (статус и тело ответа — требуется решение команды) | Время завершения, отсутствие зависаний, тип ошибки | k6 summary (duration), логи без стек-трейсов, счётчик таймаутов | k6; staging с прокси/mock LLM, эмулирующим задержку |
| SEC-1/OBS-1: отсутствие утечек в логах | 10 RPS, 10 мин; в diff синтетические маркеры секретов | 0 вхождений секретов/диффа/ответов в логах; логи содержат только request_id, длительность, статус | Количество совпадений по шаблонам секретов в логах | Отчёт поиска по логам (паттерны), пример строк без содержимого | k6; доступ к логам приложения/инфраструктуры |
| OUT-1/QA-1: формат ответа под нагрузкой | 20 RPS, 10 мин; типовые диффы | 100% ответов валидны по OUT-1; risks ≤ 3; нет approve/merge/edit | Доля валидных ответов, нарушения OUT-1 | Валидатор схемы (отчёт), k6 checks | k6; валидатор схемы OUT-1 на клиенте |

Примечание: значения RPS ориентировочные. Финальные целевые профили задаются продуктовой и платформенной командами. Места, где требуется уточнение, помечены "Требуется решение команды".

## Метрики и пороги (pass/fail)

- Метрики: p50/p90/p99 латентности (мс), RPS, коды 2xx/4xx/5xx, timeouts, доля 413, CPU/Memory/Saturation (если доступно), счётчик обращений к внешнему LLM.
- Общие пороги для стабильных сценариев (Baseline/Ramp/Spike восстановление/Soak):
  - Ошибки 5xx = 0; timeouts = 0.
  - p50 < 200 мс; p90 < 400-500 мс; p99 < 800-1200 мс в зависимости от сценария (см. таблицу).
  - CPU/Memory процесса сервиса < 70% пиково, без тренда роста на Soak (>5% после прогрева считается провалом).
- API-1: доля 413 = 100% при входе > 20 000 символов; 5xx = 0; счётчик вызовов LLM = 0.
- REL-1: каждый запрос завершён ≤ 11 с с контролируемым ответом; отсутствие зависаний; 5xx = 0 (точный статус/тело ответа согласовать).
- SEC-1/OBS-1: 0 совпадений по регулярным выражениям секретов и отсутствуют фрагменты diff/ответов в логах; в логах только request_id, длительность и статус.
- OUT-1/QA-1: 100% ответов валидны по схеме OUT-1; risks ≤ 3.

Требуется решение команды:
- Целевые RPS для Baseline/Spike/Stress.
- Точный статус/формат контролируемой ошибки при таймауте LLM (REL-1).
- Источник телеметрии CPU/Memory и формат логов.

## Среда, инструменты и безопасность

- Инструмент нагрузки: k6 OSS v0.49+.
- Валидация ответа: клиентский валидатор схемы OUT-1 (локальный скрипт/библиотека).
- Стенд: staging с:
  - стабильной конфигурацией (версия сервиса зафиксирована тегом),
  - предсказуемыми лимитами (rate limits, quotas),
  - доступной телеметрией (метрики/логи),
  - безопасными синтетическими данными (дифф без реальных секретов/кода).
- Политика данных (SEC-1/OBS-1):
  - запрещено использовать реальные секреты,
  - запрещено логировать содержимое diff и ответы модели,
  - допускается хранение только технических метрик и агрегатов.

## Порядок запуска и воспроизводимость

1. Зафиксировать версии: сервис (git tag/commit), k6 (v0.49+), конфигурацию стенда.
2. Подготовить переменные окружения:
   - BASE_URL=https://staging.example/api
   - TOKEN=<тестовый токен без доступа к прод>
   - LLM_PROXY_URL (для REL-1) — mock/прокси, умеющий задерживать ответы.
3. Подготовить k6-скрипт (пример):
   - POST на `${BASE_URL}/reviews` с заголовками `Authorization: Bearer ${TOKEN}`, `Content-Type: application/json`.
   - Тело: `{ "diff": "...синтетический diff..." }` (для API-1 — строка длиной > 20000 символов; для SEC-1 — маркеры секретов вида `SECRET_TOKEN_XYZ`).
   - checks: статус-коды, схема OUT-1 (для OUT-1/QA-1), измерение латентности.
4. Запуск сценариев k6:
   - Baseline: `k6 run -e BASE_URL=$BASE_URL -e TOKEN=$TOKEN --vus 50 --duration 10m scripts/reviews.js --summary-export=artifacts/baseline.json`
   - Ramp: использовать stages, пример `--stage 2m:0,8m:100,10m:100,10m:0` (или файл со сценарием), экспорт `artifacts/ramp.json`.
   - Spike: stages с резким пиком, экспорт `artifacts/spike.json`.
   - Stress: ступени по 50 RPS, экспорт `artifacts/stress.json` и отдельная сводная таблица RPS→SLO.
   - Soak: `--vus 30 --duration 2h`, экспорт `artifacts/soak.json`.
   - API-1: генерация тела > 20000 символов, ожидание 413, экспорт `artifacts/api1_413.json`.
   - REL-1: направить трафик через LLM_PROXY_URL с задержкой > 10 c, экспорт `artifacts/rel1_timeout.json`.
   - SEC-1/OBS-1: прогон с маркерами секретов; затем проверка логов.
5. Сбор Evidence:
   - JSON-summary k6, скриншоты/экспорты графиков телеметрии,
   - протокол поиска по логам (регексы секретов; без вставки содержимого diff/ответов),
   - сводная таблица порогов и фактических значений, решение о безопасном лимите (из Stress).
6. Повторяемость: все команды и параметры сохраняются в `artifacts/run_<YYYYMMDD_HHMM>.md` с указанием версий и seed генераторов.

## Когда нагрузочные тесты откладываются

Нагрузочные тесты можно временно отложить, если одновременно выполняются условия:
- API нестабилен или отсутствуют реализованные SEC-1, API-1, REL-1, OUT-1 (хотя бы один из этих базовых инвариантов не соблюден).
- Нет изолированного staging-стенда с телеметрией.
- Нет синтетических тестовых данных без секретов.
- Набор функциональных тестов ещё флапает (нестабилен).

Включение нагрузочных тестов при выполнении входных условий:
- Реализованы и проверены SEC-1, API-1, REL-1, OUT-1, OBS-1.
- Доступна телеметрия (метрики, логи без содержимого diff/ответов).
- Есть согласованные целевые профили RPS и пороги SLO (или пометки "Требуется решение команды").

## Как использовали AI

- Для чего: структурирование и расширение плана нагрузочного тестирования с привязкой к правилам SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1.
- Что проверили и исправили сами: ввели явные пороги pass/fail, добавили сценарии ramp/spike/stress/soak и негативные; уточнили Evidence и требования к стенду; исключили примеры с реальными секретами/контентом diff.
- Ограничения: без доступа к внешней сети и без изменения исходного кода; места для решений команды помечены.
