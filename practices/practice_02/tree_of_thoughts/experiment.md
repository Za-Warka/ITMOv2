# Tree of Thoughts

- Решение, для которого нужны альтернативы: подход к нагрузочному тесту POST /api/reviews (инструмент и структура сценариев: единый сценарий с комбинированными проверками vs раздельные сценарии; k6 vs Locust).
- Критерии выбора: соответствие SEC-1, API-1, REL-1, OBS-1; простота запуска локально (50 RPS, 5 минут); наличие телеметрии (request_id, длительность, статус) без логов содержимого; проверяемость порогов (p50 < 200 мс, 5xx = 0, 413 при >20k); воспроизводимость и читаемость отчётов.

## Запрос

Выбрать инструмент и структуру сценария для P1-03, чтобы в одном процессе проверки обеспечить baseline ≤20k, near-timeout (≈10 с по REL-1) и кейс >20k (HTTP 413) при соблюдении OBS-1.

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A | k6, единый сценарий: группы/tags для baseline ≤20k, near-timeout (искусственная задержка LLM ≈10 с), >20k (ожидаем 413); thresholds и checks в одном запуске. | Смешение профилей в одном прогоне усложняет разбор; нужна заглушка/инъекция задержки внешнего LLM. | Соответствует всем правилам; низкая сложность; высокая воспроизводимость и читаемость отчёта k6. |
| B | Locust, раздельные сценарии: отдельные свиты для baseline и для >20k; near-timeout в отдельном task. | Больше кода и инфраструктуры; сложнее выразить пороги p50/5xx на уровне свитов; отчёты менее стандартизированы. | Правилам соответствует; средняя сложность; воспроизводимость ниже из-за ручных порогов. |
| C | k6, два отдельных запуска: run1 baseline+near-timeout; run2 — только >20k для 413. | Два запуска и два отчёта; выше время и риск рассинхронизации конфигов. | Правилам соответствует; сложность средняя; воспроизводимость высокая, но затраты времени выше. |

## Выбор

- Выбранная альтернатива: A (k6, единый сценарий с группами и порогами).
- Почему: соответствует evidence в tests_load (Инструмент: k6), минимальная операционная сложность, один отчёт, встроенные thresholds (p50, 5xx, 413 как checks), легко тегировать группы baseline/near-timeout/>20k.
- Как проверим: прогон локально на стенде с телеметрией; проверка сбора request_id/длительность/статус; эмуляция near-timeout ≈10 с и контрольного ответа по REL-1; отправка diff > 20 000 символов и ожидание HTTP 413 без вызова LLM (по телеметрии); проверка отсутствия логирования содержимого (OBS-1).
