Для этой практики я выбрал GitHub Spec Kit и добавил в Repo Atlas две фичи: ссылку на выбранную эпоху и экскурсию по истории проекта. Для каждой отдельно подготовили спецификацию, план и задачи, провели анализ и ревью требований, затем реализовали и проверили результат.

Польза спецификации стала заметна на деталях. Например, для ссылки понадобилось сохранять точную дату, чтобы после открытия не менялось число коммитов. Для экскурсии пришлось заранее определить, какие события выбирать и как учитывать ботов и неполную историю. Такие вопросы легко пропустить, если сразу просить агента писать код.

Для двух небольших фич процесс получился довольно объёмным: документов много, и их тоже нужно проверять. При этом разделение работы помогло сначала закончить одну фичу, а потом перейти ко второй. После первой проходили 77 тестов, после второй — 88; интерфейс дополнительно проверили в браузере. Для себя я вынес, что Spec Kit помогает структурировать работу, но наличие спецификации само по себе не заменяет проверку результата
